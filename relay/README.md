# Релей Telegram Bot API (Yandex Cloud kz1)

Зачем и почему именно так — в аналитической записке «Сбои Telegram-бота при размещении
инфраструктуры в Yandex Cloud» (сентябрь 2026). Коротко:

- С сентября 2026 **api.telegram.org недоступен с любых серверов в РФ** — ТСПУ режет все
  подсети Telegram на исходящем. Пин IP `149.154.167.220`, который спасал летом, мёртв
  (проверено 21.09.2026: все IP Telegram с ВМ `faqbot` уходят в таймаут).
- Смена облака не поможет, webhook не поможет (блок двусторонний), «обход DPI» на сервере
  устойчиво не работает.
- **Решение:** reverse-proxy за пределами РФ + long polling. База, лог, обращения к Yandex AI
  Studio — по-прежнему в Yandex Cloud (РФ). Релей ничего не хранит и не логирует — это
  не база данных, требование локализации (ч. 5 ст. 18 152-ФЗ) он не затрагивает.
- Регион **Yandex Cloud kz1** (Казахстан): страна из перечня с адекватной защитой ПДн,
  передача допускается сразу после уведомления РКН.

Схема:

```
Пользователь Telegram ──► Telegram (ОАЭ) ◄──HTTPS── релей nginx (YC kz1, Казахстан)
                                                         ▲ только с IP бэкенда
                                                         │ HTTPS, Let's Encrypt
                                      бот faqbot (YC ru-central1, РФ) ── long polling
                                        база · лог · Yandex AI Studio — в РФ
```

---

## Шаг 1. ВМ в Yandex Cloud Казахстан — делает владелец облака

Yandex Cloud Казахстан — **отдельная инсталляция** со своей консолью, биллингом и IAM.
Наш сервисный аккаунт `leonov-deployer` там не существует (`Subject not found` при
обращении к `api.yandexcloud.kz`), поэтому купить ВМ автоматически нельзя.

1. Консоль: **https://kz.console.yandex.cloud** · биллинг: **https://kz.center.yandex.cloud/billing**.
   Нужен платёжный аккаунт в казахстанской инсталляции. ⚠️ Принимает ли она российскую карту
   или юрлицо — не проверено; если нет, это вопрос к поддержке/менеджеру Yandex Cloud.
2. Создать ВМ (Compute Cloud → Создать):
   - образ **Ubuntu 22.04 LTS**;
   - зона **`kz1-a`**;
   - самая маленькая конфигурация: 2 vCPU с долей 5–20 %, 1 ГБ RAM, 10 ГБ HDD — релей
     почти ничего не потребляет;
   - **публичный IPv4**, лучше статический (адрес релея прописывается в конфиг бота);
   - логин `yc-user`, SSH-ключ — вставить:
     ```
     ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIDpIvzcGzV3CfaEUsDyg7VwCARZKACcQbmNRbUcVSn02 faqbot-vm
     ```
     (это ключ `~/.ssh/yc_faqbot_key`, которым обслуживаются остальные ВМ).
3. Сообщить публичный IP новой ВМ.

Ориентир по цене: такая ВМ в РФ стоит ~500–800 ₽/мес; в kz1 тарифы в тенге, порядок тот же.

## Шаг 2. Установка релея — одна команда

С локальной машины:

```bash
scp -i ~/.ssh/yc_faqbot_key relay/install-relay.sh yc-user@<IP_РЕЛЕЯ>:/tmp/
ssh -i ~/.ssh/yc_faqbot_key yc-user@<IP_РЕЛЕЯ> "sudo bash /tmp/install-relay.sh 89.169.142.74"
```

`89.169.142.74` — публичный IP ВМ `faqbot` в РФ: только ей будет разрешён доступ к релею.

Скрипт: проверяет, что Telegram отсюда доступен → ставит nginx, certbot, ufw → получает
сертификат Let's Encrypt на имя `<IP>.sslip.io` (публичный DNS-сервис, свой домен не нужен)
→ пишет конфиг reverse-proxy → делает самопроверку. В конце печатает строку для `.env` бота.

Что делает конфиг (см. текст скрипта):
- `allow <IP бэкенда>; deny all;` + ufw — открытый релей был бы бесплатным прокси к Telegram
  для кого угодно с любым токеном;
- `access_log off` — тела запросов и токен бота в логах не появляются;
- `resolver` + переменная в `proxy_pass` — nginx перерезолвит api.telegram.org каждые 5 минут;
- `proxy_read_timeout 120s` — под long polling.

## Шаг 3. Переключение бота

На ВМ `faqbot` (89.169.142.74), в `/opt/faqbot/.env`:

```
TELEGRAM_RELAY_URL=https://<IP-с-дефисами>.sslip.io
```

затем `cd /opt/faqbot && sudo docker compose up -d --build` (код бота обновлён: читает
`TELEGRAM_RELAY_URL` и подставляет его в `base_url`/`base_file_url`; из `docker-compose.yml`
убран мёртвый пин `extra_hosts`).

Проверка с ВМ бота:

```bash
curl -s https://<релей>/relay-health                  # ok
curl -s https://<релей>/bot<TOKEN>/getMe              # {"ok":true,...}
sudo docker logs -f faqbot                            # getUpdates ... 200 OK
```

Требование записки «инициализация Telegram-клиента вынесена в фоновый процесс, чтобы
недоступность релея не блокировала сервис» выполнено архитектурно: Telegram-бот (`faqbot`)
и MAX-бот (`maxbot`) — отдельные контейнеры. Релей упал → перезапускается только `faqbot`
(`restart: unless-stopped`), MAX-канал не замечает.

## Эксплуатация

- **Сертификат** продлевается сам (таймер certbot, порт 80 открыт для этого). Проверить:
  `sudo certbot renew --dry-run`.
- **Сменился IP бэкенда** (ВМ пересоздали): повторно запустить `install-relay.sh <новый IP>`.
- **Сменился IP релея:** перевыпустить сертификат (скрипт сделает сам, имя изменится) и
  обновить `TELEGRAM_RELAY_URL` в `.env` бота.
- **Диагностика:** `sudo tail /var/log/nginx/telegram-relay.error.log` на релее; с ВМ бота
  `curl -sv https://<релей>/relay-health`. Код 403 = IP бэкенда не в allowlist.
- **Откат:** убрать `TELEGRAM_RELAY_URL` из `.env` — бот пойдёт в api.telegram.org напрямую
  (сейчас это не работает, но код прежний).

## Что остаётся за пределами техники (из записки)

- **Юридическое заключение по ч. 8 ст. 10 149-ФЗ** (запрет иностранных мессенджеров при
  выполнении гос./муниципального задания; Telegram — в перечне). Записка рекомендует получить
  его **до** работ по релею: при отрицательном ответе единственным каналом остаётся MAX.
- **Уведомление РКН о трансграничной передаче** — отдельно от уведомления об обработке,
  с указанием ОАЭ (Telegram) и Казахстана (релей).
- **Схема потоков данных** и **политика обработки ПДн** — привести в соответствие.
- Зафиксировать: **MAX — основной канал, Telegram — дополнительный.**
